# 专利写作经验沉淀（Harness）

## Overview

本 skill 用于**专利写作过程中的经验提取、矛盾识别与规则归纳**。它不撰写专利、不修改专利，而是在用户完成专利修改后，自动从对话历史中提取有价值的工作经验，存入结构化的经验库，供后续同类专利参考复用。

核心思想来自《矛盾论》：不同质的矛盾用不同质的方法解决。专利写作的每个 SOP 环节都有其固有矛盾，记录经验不是记录"改了哪个数字"，而是记录"这个环节遇到了什么矛盾、怎么解决的"。

## 触发条件

满足以下任一条件时触发：

- 用户调用了 `patent-cn-edit` 的"结束修改，导出最新版 docx"选项
- 用户说"结束修改"、"定稿"、"就这样吧"、"可以了"
- 连续 3 轮没有实质性修改
- 用户显式调用 `/patent-harness` 命令

## 专利写作 SOP 骨架

所有经验记录必须挂到以下骨架的对应环节下。这是专利写作的标准流程，每个环节都有固有矛盾：

```
专利写作 SOP 骨架
├── 1. 交底书理解
│   └── 固有矛盾：交底信息不完整 vs 申请文件需要完整
├── 2. 技术方案确定
│   └── 固有矛盾：技术效果最大化 vs 可实施性/支持性
├── 3. 撰写权利要求
│   └── 固有矛盾：保护范围最大化 vs 授权概率
├── 4. 撰写说明书
│   ├── 4.1 摘要
│   ├── 4.2 背景技术
│   ├── 4.3 发明内容（技术问题 / 技术方案 / 有益效果）
│   └── 4.4 附图说明
├── 5. 撰写具体实施方式
│   ├── 5.1 实施例
│   ├── 5.2 对比例
│   └── 5.3 对比总结
├── 6. 自查与交付
│   └── 固有矛盾：交付质量 vs 时间成本
└── 7. 答复审查意见（如有）
    └── 固有矛盾：坚持核心技术 vs 妥协以获授权
```

## 矛盾分类框架

识别出的矛盾必须归入以下四类之一（不同性质用不同方法）：

| 矛盾性质 | 定义 | 典型 SOP 环节 | 处理方法 |
|---------|------|-------------|---------|
| **信息矛盾** | 信息不足 vs 需求完整 | 交底书理解 | 追问、补充、占位 |
| **利益矛盾** | 两个合法目标互相排斥 | 撰写权利要求、答复审查 | 权衡、分级策略 |
| **资源矛盾** | 理想要求 vs 可用资源 | 具体实施方式 | 最小充分性判断 |
| **立场矛盾** | 不同利益方的诉求冲突 | 答复审查意见 | 区分核心与非核心 |

### 矛盾记录模板（_template.md）

每条矛盾记录格式如下：

```markdown
## [YYYY-MM-DD] 专利：[专利名称/标识]

**SOP 环节**：[如 3. 撰写权利要求]
**矛盾性质**：[信息/利益/资源/立场]
**主要矛盾**：[如 保护范围 vs 授权概率]
**次要矛盾**：[如有，如 参数上位化层级 vs 审查员偏好]

### 情境
- 技术领域：[如 湿法碳化混凝土]
- 案例特征：[如 方法+产品双独权、2条独权、审查员张三]
- 阶段标记：[如 第1轮修改 / 初稿 / 答复阶段]

### 矛盾描述
[具体描述矛盾是什么——不是"改了温度"，而是"温度写具体了保护范围窄，写宽了说明书不支持"]

### 操作
[实际采取的处理方式——分级策略、追问补充、占位等]

### 结果
- 短期：[如 本轮审查通过 / 被要求修改]
- 长期：[如 最终授权 / 仍存争议，待后续专利验证]
- 遗留矛盾：[如 保护范围已妥协，答复阶段可能爆发，标记为遗留]

### 归因
- [ ] 内因问题（专利质量本身）
- [ ] 外因问题（审查员风格/理解差异）
```

### 领域规则模板

规则归纳后的格式：

```markdown
# [技术领域] — 领域规则

> 最后归纳时间：YYYY-MM-DD
> 归纳自 N 条矛盾记录

## SOP 环节 X：[环节名称]

### 矛盾：[矛盾名称]

**规则**：[一句话规则]
**理由**：[为什么这样做的因果解释]
**适用条件**：[在什么情境下适用，如技术领域、审查员类型]
**反例**：[什么情况下不适用]
**来源**：[来自哪些矛盾记录]
**状态**：[✅ 稳定 / ⚠️ 需复查 / ❌ 已废弃]
```

### 遗留矛盾模板

```markdown
# 遗留矛盾清单

> 被搁置的矛盾可能在下一轮 SOP 环节或下一个专利中爆发

## [来源专利] → [目标环节]

- 矛盾：[描述]
- 触发条件：[什么情况下会爆发]
- 当前状态：[未处理 / 已在目标专利中处理 / 已确认无需处理]
```

## 工作流程

触发后严格按以下步骤执行。

### Step 1：判断当前专利的技术领域

先判断本轮对话涉及的专利属于哪个技术领域，用于选择经验文件的存储路径。

技术领域识别优先级：
1. 用户显式指定（"这是湿法碳化混凝土的专利"）
2. 从交底书/专利稿中推断（"交底书提到了碳化再生细骨料"→ 湿法碳化混凝土）
3. 无法识别时标为"未分类"，人工归类

### Step 2：扫描对话，提取矛盾-经验对

读取本轮对话的完整历史（如对话已被压缩，读取 `workspace/patent-draft.md` 的修改记录），按 SOP 骨架逐环节扫描，识别：

1. **改了什么？**（定位到 SOP 环节）
2. **为什么之前那个版本不行？**（矛盾描述——不是具体数据，是结构性矛盾）
3. **怎么解决的？**（操作方法）
4. **结果如何？**（验证结果）

**关键**：只记录**实质性矛盾**，不记录格式调整（错别字、标点、段落缩进）。判断标准：

```
这条修改是否影响了专利的实质性内容（保护范围、创造性、支持性）？
  → 是：记录
  → 否：跳过
```

### Step 3：标记矛盾性质和归因

对每条识别出的矛盾：

- **定性**：信息/利益/资源/立场 四选一
- **归因**：内因（专利质量问题） vs 外因（审查员风格）
- **识别遗留**：如果矛盾被妥协处理（而非彻底解决），标记为"遗留矛盾"

### Step 4：写入矛盾记录

将提取的矛盾-经验对追加到对应技术领域的 `矛盾记录.md` 文件中。如果该领域的目录不存在，先创建。

**追加模式**：新记录追加到文件末尾，不覆盖已有记录。

### Step 5：规则归纳（阈值触发）

检查当前技术领域的矛盾记录数量：

- **< 3 条**：仅记录，不归纳
- **≥ 3 条**：触发规则归纳——让 agent 读取全部矛盾记录，按 SOP 骨架归类，归纳出领域规则，写入 `领域规则.md`
- **≥ 10 条**：触发规则迭代检测——检查是否有规则被连续偏离 2 次以上，标记为"⚠️ 需复查"

**归纳原则**：
- 每条规则必须附带"理由"——没有理由的规则不可信
- 规则必须标注"适用条件"——同一规则在不同技术领域/审查员下可能不适用
- 规则归纳是草案，人工可以后续修正

### Step 6：遗留矛盾追踪

如果本轮有被妥协处理的矛盾（如"保护范围暂时缩小，答复阶段再争取"），写入 `遗留矛盾.md`：

```markdown
## [专利标识] → 答复审查意见阶段

- 矛盾：权利要求保护范围已妥协（独权从 2 条减为 1 条）
- 触发条件：进入答复审查意见阶段时
- 当前状态：未处理
```

### Step 7：输出总结

向用户输出本次经验沉淀的结果：

```markdown
## 经验沉淀完成

本次提取矛盾：**N 条**
涉及 SOP 环节：[如 3. 撰写权利要求 / 5.3 对比总结]
技术领域：[如 湿法碳化混凝土]
规则状态：
  - 新增规则：N 条
  - 标记需复查：N 条（如"独权数量规则"连续被偏离 2 次）
  - 遗留矛盾：N 条

经验文件路径：
- 矛盾记录：`skills/custom/patent-cn-harness/experiences/[技术领域]/矛盾记录.md`
- 领域规则：`skills/custom/patent-cn-harness/experiences/[技术领域]/领域规则.md`
- 遗留矛盾：`skills/custom/patent-cn-harness/experiences/[技术领域]/遗留矛盾.md`
```

## 与现有专利 skill 的分工

| Skill | 职责 |
|-------|------|
| `patent-cn-core` | 从零撰写专利（交底→申请文件） |
| `patent-cn-edit` | 已有专利稿的局部修改 |
| `patent-cn-harness` | 经验提取、矛盾识别、规则归纳 |
| `patent-domain-*` | 领域术语与实施例习惯 |

Harness 不写专利、不改专利——它只读对话、写经验。

## 强约束

1. **禁止**记录格式调整（错别字、标点、缩进）为矛盾
2. **禁止**编造矛盾或结果——只记录对话中真实发生的
3. **禁止**覆盖已有经验记录——始终追加
4. **禁止**记录具体实验数值为矛盾——矛盾是结构性的，不是数据性的
5. **禁止**将外因问题归因为内因（如审查员理解偏差不是专利质量问题）

## 行为准则

1. **结构优先**：记录矛盾时先看 SOP 环节和矛盾性质，再看具体操作
2. **简洁记录**：每条矛盾不超过 300 字，强制聚焦核心
3. **理由必写**：规则归纳必须附带"为什么"，没有理由的规则不可信
4. **遗留追踪**：被妥协的矛盾必须标记为遗留，不追踪的妥协等于白妥协
