# 中国专利撰写（核心）

## 本 skill 解决什么

你在带代理师把**交底事实**整理成**可申请文本**，并帮其发现**形式与支持**上的风险点。这样做的原因是：申请文件既要满足撰写规范，又要给代理人留出**署名与定稿**空间，避免模型越权作出法律终局结论。

**分发与使用**：`references/` 为 Markdown 规则；**`resources/samples/`** 内预置若干**样板专利 PDF**（优先带**可抽取文字层**，可随仓库分发；`read_file` 对版式，亦可用 `pypdf`/PyMuPDF/`pdftotext` 离线转 `.md` 作全文参考）。《审查指南》全文仍见 `resources/README.md`（默认不纳入 Git）。复制整包 `patent-cn-core/` 即可。详见 `references/style-samples-and-attachments.md` 与 `resources/README.md`。

**与 `pdf` skill**：需要从 PDF **批量抽取全文、表格或做 OCR** 时，先按需 `read_file` 技能 **`pdf`** 的主文件（`skills/public/pdf/SKILL.md`，容器内路径以对话里 `<skill>` 的 `location` 为准），再按其中 **pypdf → pdfplumber →（扫描件再）OCR** 的顺序执行；专利 skill 负责「读哪份材料、对照什么规则」，`pdf` skill 负责「提取技术细节」。

## 超长上下文与对话承接

1. **平台层**：部署在 `config.yaml` 中启用 `summarization` 时，由中间层对旧消息做自动摘要（效果类同外置「递归摘要」工具，但无需单独注册 `summarize` 工具）。可按负载调整 `trigger`、`keep`、`trim_tokens_to_summarize`；若希望摘要模型优先保留申请文件要素，可设置全局 `summary_prompt`。
2. **本 skill**：在继续撰写或大改前，若上下文紧张或历史已被压缩，先输出不超过约 400 字的 **《对话承接稿》**，须保留：交底核心方案与区别特征、已定术语与附图标记对照、权利要求现状（独立项骨架与从属项号及各自挂点）、说明书各节完成度、已确认事实与「待代理人核实」汇总、未补实验/参数/文献。后续输出只依据承接稿推进，避免假设仍存在于上下文中的长原文细节。
3. **不要**在承接稿中写入内部样板路径或公告号。

## 工作流（按顺序做）

1. **确认输入类型**：交底节选、现有权利要求、审查意见摘录、或「从零起草某节」——缺什么材料先列问题，再动笔。
2. **对齐结构**：说明书按六块推进（见下节）。用户要**整套申请文件/说明书全文**时，须同时输出**说明书摘要**：**连续一段、不设标题行**，**含标点不超过 300 字**，内容含**名称、领域、问题、方案要点、用途**——详见 `references/abstract-summary.md`（与《专利审查指南》第一部分说明书摘要形式要点一致）。**发明内容**第三节：技术问题用**段落**写；**技术方案与从属限定合并为同一块连贯叙述**（用「优选地」等嵌入），**不要**照搬交底书里「4.2 技术方案 / 4.3 从属技术方案」分节；**有益效果**须写清且与方案、问题相呼应，**可用一个或多个段落分段**表述（不必与方案挤在同一段）；方案记载须与**权利要求书逐项可对上**（见 `references/specification-and-claims.md`「发明内容」小节）。权利要求**先独立后从属**，正式稿**仅用连续编号**，**禁止**用 Markdown 二级标题按主题拆权项——详见 `references/claims-layout-and-numbering.md`。
3. **标注三类内容**：(a) 来自用户的事实；(b) 你的推断，前缀「待代理人核实：」；(c) 指南或法条，仅写原则并提醒核对现行文本，**不编造具体款号**。
4. **每节输出节奏**：先给「本节小标题 + 段落要点」，再给正文草稿，最后给「代理人需补资料/需拍板」清单。
5. **创造性/新颖性**：只整理「区别特征—技术问题—效果」链条与论据草稿，**不写「必然授权/必然驳回」**。

## 质量门禁（专利输出前必过）

以下门禁用于把交底书稳定转换为中国专利申请文本。任一未满足时，先补全再交付。

1. **信息补全门禁**：先输出《关键信息缺失清单》（建议不超过 12 项），格式为「缺失信息-影响-建议补充内容」；信息不足时先给《暂定假设表》，并在正文中标注「待代理人核实：」。
2. **权利要求门禁**：权利要求总数以 **10～16 项** 为常规区间（按交底创新点层次与说明书支持情况伸缩，避免为凑数削足适履）。**独立权利要求**：默认 **1 项** 写清主发明点的全部必要技术特征（区别特征进独权，非必要特征下沉从属）。仅当交底或已确认的暂定假设中存在 **可并列保护且说明书能分别充分支持** 的不同完整技术方案时，可增设 **第二项** 独立权利要求，且与首项在类型上并列互补（如装置/产品与制造或使用该方法等）；**不得**为追求「多类型独权」而硬套客体不适配或缺乏支持的「空壳」独权。用词简练；自定义术语首次出现须在说明书中有定义或明确指称；避免空泛纯功能词与无依据的未量化断言。
3. **背景技术门禁**：必须写明现有技术、现有方案、最接近技术、现有缺陷，并确保这些缺陷能由本申请方案对应解决；**不得虚构**具体文献、实验或产品型号——无据处用概括性表述并标「待代理人核实：」。
4. **技术效果门禁**：有益效果 **不少于 6 条**；若交底可归纳的可验证效果不足 6 条，则列出现有条目并单列「交底未载明、待补充以支撑之效果」类说明，**不得**编造效果或数据。每条尽量对应具体特征、结构、方法/工艺步骤、装置或性能指标之一，不写营销式口号。
5. **实施例门禁**：至少 **3 个实施例 + 2 个对比例**，围绕权项技术点安排对比逻辑。交底已载明的原料牌号、工艺参数、测试条件、标准编号等 **照录**；交底未给出的数值、对比结果、标准编号等一律用 **「XX」「待补」** 等占位，**禁止编造**实验或检测数据。对比例与实施例在交底允许范围内保持除关键区别特征外的条件一致（交底未写处同样占位）。测试方法仅在有交底依据或公认规范可指称时写具体标准号，否则写「标准号待补」或指向交底段落。
6. **范围概括门禁**：关键成分/步骤先写上位概念，再写优选范围与可选项（例如溶剂、温度、比例、工艺路径），避免保护范围过窄。**权利要求书中禁止使用点值**：当交底书给出多个离散数值（如 800℃、1000℃）时，必须合并为范围值（如 800~1000℃），不得以顿号、逗号或空格罗列多个点值；范围分隔符统一用 `~`。
7. **交付分层门禁**：交付须区分 **（A）递交用文本**：说明书六部分 + 权利要求书 + 说明书摘要，体例符合常规申请文件，**不夹带**「进一步改进建议」「待审核」等非递交章节；**（B）代理人工作附件**（对话中单独成章或另存为工作稿）：至少含「进一步改进建议」与「待审核」（数据/范围/机理矛盾、概括过宽或过窄疑问、待核实事实），与《待申请人确认事项》互补，**不替代**代理人法律判断与定稿。
8. **合规自检门禁**：交付前附《待申请人确认事项》与《合规自检清单》（清楚性、支持性、单一性、可实施性、术语一致性）。

## 交付格式策略（专利中文场景）

1. **默认交付 `docx`**：用户请求“下载文稿/导出专利”且未指定格式时，默认产出 `docx`，不要默认给 `md`。
2. **`md` 仅作为中间产物**：允许先在沙箱内生成 `md` 供组稿或审阅，但最终交付文件优先转为 `docx`。
3. **用户坚持要 PDF 时**：先交付 `docx`，并明确建议用户在本机 **Word/WPS** 中“另存为 PDF”（中文兼容性更稳）。
4. **仅在用户明确要求“直接生成 PDF”时**，再走 `doc-convert`，并在命令中显式使用 `--force-direct-pdf`；同时提示“若出现中文乱码，请改用 docx 本地导出 PDF”。


## Markdown 格式要求（⚠️ 确保 Word 标题样式）

所有章节标题**必须**使用 Markdown 语法，确保 `pandoc` 转换后保留层级样式：

| 层级 | Markdown 写法 | Word 效果 | 匹配示例 |
|------|--------------|----------|----------|
| 一级标题 | `# 1. 技术领域` | 标题 1 | `# 1. 技术领域` / `# 一、背景技术` |
| 二级标题 | `## 3.1 技术方案` | 标题 2 | `## 3.1 优选方案` / `## 实施例 1：` |
| 三级标题 | `### 实施例 1：` | 标题 3 | `### 3.1.1 参数设置` |

### 关键规则

1. **禁止纯文本标题**：`1. 技术领域`（不带 `#`）会被当作普通段落，转换后无标题样式
2. **空格要求**：`#` 后必须跟一个空格，如 `# 标题` 而非 `#标题`
3. **标点兼容**：支持中文/英文标点变体，如 `一、` / `1.` / `1．` 均可
4. **摘要特殊处理**：使用 `# 摘要` 作为一级标题，正文直接开始写内容
5. **权利要求书特殊处理**：使用 `# 权利要求书` 或 `# 2. 权利要求书`，正文保持连续编号

### 示例对比

✅ 正确：
```markdown
# 一种基于粗粉预钝化的低氧烧结钕铁硼粉末制备方法

# 摘要

（正文内容...）

# 1. 技术领域
本发明涉及稀土永磁材料制备...

## 3.1 技术方案
优选地，预钝化处理温度为...

### 实施例 1：
按以下步骤操作...
```

❌ 错误（标题无样式）：
```markdown
一种基于粗粉预钝化的低氧烧结钕铁硼粉末制备方法

摘要
（正文内容...）

1. 技术领域
本发明涉及稀土永磁材料制备...

3.1 技术方案
优选地，预钝化处理温度为...
```

> 💡 提示：`_auto_add_headings()` 会兼容 `一、` / `1．` 等变体，但显式写 `# ` 最可靠。

## 强约束（内部参考不外泄）

1. `resources/samples/`、`references/` 中的内置样板与文献号仅用于内部校准，**不得对用户展示**（正文、摘要、回执、说明均不展示）。
2. 即使用户要求“引用对比文件”，也只能引用**用户自己提供**或**运行时外部检索得到**的文献；不得引用 skill 内置参考号。
3. 对外默认用泛化措辞（如“现有技术”“公开方案”），不要暴露内部样板编号与路径。
4. 输出前必须做一次自检：若出现 `CN` 号或内部样板路径，先删除/改写再交付。

## 说明书正文与摘要（与用户约定按块写）

**说明书摘要**（递交件常单独成页；撰稿时勿漏）：**以 `# 摘要` 作为一级标题**，正文一段到底、≤300 字（含标点）、内容含名称/领域/问题/方案要点/用途、勿商业宣传——见 `references/abstract-summary.md`。

**完整文档输出顺序**（交付件，不可省略）：

**摘要** → **权利要求书** → **1. 技术领域** → **2. 背景技术** → **3. 发明内容** → **4. 附图说明** → **5. 具体实施方式** → **进一步改进建议** → **待申请人确认事项**

1. 摘要（以 `# 摘要` 为标题，正文≤300 字，一段到底）  
2. 权利要求书（独立项 + 从属项，连续编号，**紧接摘要之后**）  
3. 技术领域  
4. 背景技术  
5. 发明内容（**技术问题**段落叙述；**技术方案**一条流，从属用「优选地」等并入，**勿单设「从属技术方案」节**；**有益效果**写明且可与问题/方案呼应，**允许多段分段**；整体与**全部权项**可对上，见 `specification-and-claims.md`）  
6. 附图说明（无图则写明不适用或从略）  
7. 具体实施方式（与权利要求可对上、本领域可实施；**实施例/对比例标题**单行 `实施例1：` / `对比例1：` + 全角冒号，正文另起段——见 `specification-and-claims.md`）  
8. **进一步改进建议**（必填，见下方模板）  
9. **待申请人确认事项**（必填，见下方模板）

## 交付件尾部固定章节（必填）

以下两个章节**必须**出现在专利输出文件的末尾，不可省略、不可合并到其他章节中。

### 进一步改进建议

根据交底书内容与说明书完成度，列出可进一步优化的方向，格式如下：

```
## 进一步改进建议

1. [改进方向一]：简述可补充或优化的内容（如实验数据、参数范围、对比实验等）
2. [改进方向二]：简述……
3. [改进方向三]：简述……
```

- 至少列出 **3 条** 改进建议；交底信息充分时可适当减少，但**不得少于 1 条**
- 每条建议需指出**当前缺失/不足的内容**及**建议补充的方向**
- 不得编造具体数据，仅给出建议方向

### 待申请人确认事项

列出需要申请人/发明人确认的关键信息，格式如下：

```
## 待申请人确认事项

1. [确认项一]：需要确认的具体内容（如具体参数、原料牌号、测试设备等）
2. [确认项二]：需要确认的具体内容
3. [确认项三]：需要确认的具体内容
```

- 至少列出 **3 项** 待确认事项；交底信息完整时可适当减少，但**不得少于 1 项**
- 每项需指出**待确认的具体内容**及**对专利申请的影响**
- 包括但不限于：实验数据补充、参数范围确认、测试方法/设备型号、现有技术文献检索

## 输出骨架（权利要求讨论节可用）

```markdown
## 本节目标
## 拟采用的技术方案要点（来自交底）
## 独立权利要求构思（特征列表，条文草稿可附后）
## 从属权利要求展开方向（引用关系说明）
## 与支持说明书/实施例的对应关系
## 待代理人核实或补充
```

## 与 patent-domain-* 的分工

`patent-domain-chemistry` / `patent-domain-mechanical` / `patent-domain-electrical` 管**领域术语与实施例习惯**；本 skill 管**共通结构与审查逻辑**。若用户已选某领域 Agent，读完本文件并按需读完 `references/` 后，再读对应 domain 的 `SKILL.md`。
