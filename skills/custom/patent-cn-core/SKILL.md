# 中国专利撰写（核心）

## 本 skill 解决什么

你在带代理师把**交底事实**整理成**可申请文本**，并帮其发现**形式与支持**上的风险点。这样做的原因是：申请文件既要满足撰写规范，又要给代理人留出**署名与定稿**空间，避免模型越权作出法律终局结论。

**分发与使用**：`references/` 为 Markdown 规则；**`resources/samples/`** 内预置若干**样板专利 PDF**（优先带**可抽取文字层**，可随仓库分发；`read_file` 对版式，亦可用 `pypdf`/PyMuPDF/`pdftotext` 离线转 `.md` 作全文参考）。《审查指南》全文仍见 `resources/README.md`（默认不纳入 Git）。复制整包 `patent-cn-core/` 即可。详见 `references/style-samples-and-attachments.md` 与 `resources/README.md`。

**与 `pdf` skill**：需要从 PDF **批量抽取全文、表格或做 OCR** 时，先按需 `read_file` 技能 **`pdf`** 的主文件（`skills/public/pdf/SKILL.md`，容器内路径以对话里 `<skill>` 的 `location` 为准），再按其中 **pypdf → pdfplumber →（扫描件再）OCR** 的顺序执行；专利 skill 负责「读哪份材料、对照什么规则」，`pdf` skill 负责「提取技术细节」。

## 工作流（按顺序做）

1. **确认输入类型**：交底节选、现有权利要求、审查意见摘录、或「从零起草某节」——缺什么材料先列问题，再动笔。
2. **对齐结构**：说明书按六块推进（见下节）。用户要**整套申请文件/说明书全文**时，须同时输出**说明书摘要**：**连续一段、不设标题行**，**含标点不超过 300 字**，内容含**名称、领域、问题、方案要点、用途**——详见 `references/abstract-summary.md`（与《专利审查指南》第一部分说明书摘要形式要点一致）。**发明内容**第三节：技术问题用**段落**写；**技术方案与从属限定合并为同一块连贯叙述**（用「优选地」等嵌入），**不要**照搬交底书里「4.2 技术方案 / 4.3 从属技术方案」分节；**有益效果**须写清且与方案、问题相呼应，**可用一个或多个段落分段**表述（不必与方案挤在同一段）；方案记载须与**权利要求书逐项可对上**（见 `references/specification-and-claims.md`「发明内容」小节）。权利要求**先独立后从属**，正式稿**仅用连续编号**，**禁止**用 Markdown 二级标题按主题拆权项——详见 `references/claims-layout-and-numbering.md`。
3. **标注三类内容**：(a) 来自用户的事实；(b) 你的推断，前缀「待代理人核实：」；(c) 指南或法条，仅写原则并提醒核对现行文本，**不编造具体款号**。
4. **每节输出节奏**：先给「本节小标题 + 段落要点」，再给正文草稿，最后给「代理人需补资料/需拍板」清单。
5. **创造性/新颖性**：只整理「区别特征—技术问题—效果」链条与论据草稿，**不写「必然授权/必然驳回」**。

## 质量门禁（专利输出前必过）

以下门禁用于把交底书稳定转换为中国专利申请文本。任一未满足时，先补全再交付。

1. **信息补全门禁**：先输出《关键信息缺失清单》（建议不超过 12 项），格式为「缺失信息-影响-建议补充内容」；信息不足时先给《暂定假设表》，并在正文中标注「待代理人核实：」。
2. **权利要求门禁**：默认输出 10 项权利要求（通常 1 项独立 + 9 项从属，或按客体适配），用词简练，避免非必要技术特征、空泛功能词和未量化术语。
3. **背景技术门禁**：必须写明现有技术、现有方案、最接近技术、现有缺陷，并确保这些缺陷能由本申请方案对应解决。
4. **技术效果门禁**：有益效果不少于 5 条，且逐条对应技术方案中的可验证技术点，不写营销式描述。
5. **实施例门禁**：至少给 3 个实施例 + 2 个对比例；需要列测试条件一致性、关键参数和结果数据（可示例数据，但需标注用途）。
6. **范围概括门禁**：关键成分/步骤先写上位概念，再写优选范围与可选项（例如溶剂、温度、比例、工艺路径），避免保护范围过窄。
7. **合规自检门禁**：交付前附《待申请人确认事项》与《合规自检清单》（清楚性、支持性、单一性、可实施性、术语一致性）。

## 交付格式策略（专利中文场景）

1. **默认交付 `docx`**：用户请求“下载文稿/导出专利”且未指定格式时，默认产出 `docx`，不要默认给 `md`。
2. **`md` 仅作为中间产物**：允许先在沙箱内生成 `md` 供组稿或审阅，但最终交付文件优先转为 `docx`。
3. **用户坚持要 PDF 时**：先交付 `docx`，并明确建议用户在本机 **Word/WPS** 中“另存为 PDF”（中文兼容性更稳）。
4. **仅在用户明确要求“直接生成 PDF”时**，再走 `doc-convert`，并在命令中显式使用 `--force-direct-pdf`；同时提示“若出现中文乱码，请改用 docx 本地导出 PDF”。

## 强约束（内部参考不外泄）

1. `resources/samples/`、`references/` 中的内置样板与文献号仅用于内部校准，**不得对用户展示**（正文、摘要、回执、说明均不展示）。
2. 即使用户要求“引用对比文件”，也只能引用**用户自己提供**或**运行时外部检索得到**的文献；不得引用 skill 内置参考号。
3. 对外默认用泛化措辞（如“现有技术”“公开方案”），不要暴露内部样板编号与路径。
4. 输出前必须做一次自检：若出现 `CN` 号或内部样板路径，先删除/改写再交付。

## 说明书正文与摘要（与用户约定按块写）

**说明书摘要**（递交件常单独成页；撰稿时勿漏）：**一段到底、不用标题**；**≤300 字（含标点）**；名称、领域、问题、方案要点、用途；勿商业宣传——见 `references/abstract-summary.md`。

1. 技术领域  
2. 背景技术  
3. 发明内容（**技术问题**段落叙述；**技术方案**一条流，从属用「优选地」等并入，**勿单设「从属技术方案」节**；**有益效果**写明且可与问题/方案呼应，**允许多段分段**；整体与**全部权项**可对上，见 `specification-and-claims.md`）  
4. 附图说明（无图则写明不适用或从略）  
5. 具体实施方式（与权利要求可对上、本领域可实施；**实施例/对比例标题**单行 `实施例1：` / `对比例1：` + 全角冒号，正文另起段——见 `specification-and-claims.md`）  
6. 权利要求书（独立项 + 从属项，层次清楚）

## 输出骨架（权利要求讨论节可用）

```markdown
## 本节目标
## 拟采用的技术方案要点（来自交底）
## 独立权利要求构思（特征列表，条文草稿可附后）
## 从属权利要求展开方向（引用关系说明）
## 与支持说明书/实施例的对应关系
## 待代理人核实或补充
```

## 与 patent-domain-* 的分工

`patent-domain-chemistry` / `patent-domain-mechanical` / `patent-domain-electrical` 管**领域术语与实施例习惯**；本 skill 管**共通结构与审查逻辑**。若用户已选某领域 Agent，读完本文件并按需读完 `references/` 后，再读对应 domain 的 `SKILL.md`。

## 不要做的事

编造实验数据、对比文件内容、审查员原话或官方文书；替代代理师签字与递交决策。
泄露 skill 内置样板的公开号、文件路径或引用片段。
